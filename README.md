# Deckscribe-AI

**一个未完成的 LLM 自动生成可编辑 PPTX 的实验项目，以及一些实践经验。**

> **项目状态：已停止开发 / 仅供研究与参考**
>
> 本项目的基础流程已跑通，但最终 PPTX 的视觉质量、排版灵活性和稳定性尚未达到预期。不建议直接用于生产环境。
>
> 开源这个项目的主要目的不是推广工具，而是分享在探索 LLM 自动生成 PPT 过程中的技术实践、架构取舍和踩坑经验，希望能为尝试类似方向的开发者提供一些参考。

## 一、项目尝试解决什么问题？

目标很简单：**用户提供一段非结构化内容，LLM 自动理解并编排成一页视觉质量较高、可编辑的 PowerPoint 幻灯片。**

理想情况下，希望同时满足：

- LLM 自主理解内容、确定信息层级和版式，不依赖固定模板。
- 支持流程、框架、对比、图表、信息图形化等多种表达。
- 排版接近人工制作的咨询报告或企业战略汇报。
- 最终输出为可编辑 PPTX，而不是整页截图。
- 尽可能减少人工调整和重复的 LLM 调用。

项目使用 TypeScript、LLM API 和 PptxGenJS 实现，主要技术链路为：

```text
用户提供内容
    ↓
LLM 生成 PPT 正文
    ↓
正文分页
    ↓
逐页调用 LLM 自由编排
    ↓
Scene-Graph JSON
    ├── HTML 调试预览
    └── PptxGenJS → 可编辑 PPTX
```

后期尝试将生成方式调整为 LLM 直接输出基础 PowerPoint 图层，例如文本、形状、线条、连接线、图标等，以减少代码对页面结构的干预。

## 二、探索过的两种典型技术路线

### 路线 A：固定模板 + LLM 填充内容

这是相对成熟且稳定的路线。

通常由 LLM 负责提取、归纳和组织内容，再通过程序匹配预设模板，将文字、数据和图片填入指定位置。

**优势：**

- 页面结构与品牌风格容易统一。
- PPTX 导出和后续编辑相对稳定。
- 对模型的排版能力依赖较低。
- 更适合标准化、高频、结构相似的文档生成。

**局限：**

- 页面形式容易固化，产生明显的模板感。
- 内容过多时容易拥挤、缩字或溢出；内容过少时容易出现无意义留白。
- 复杂业务逻辑往往难以匹配预设版式。
- 模板越丰富，维护与内容适配成本越高。

固定模板并不是不好的方案。对于标准化报告，它可能是更合理的工程选择。但它不符合本项目希望由 LLM 自主完成内容理解和视觉编排的目标。

### 路线 B：LLM 主导自由编排

这是本项目重点探索的方向。

由 LLM 根据当前页面内容，自行判断信息层级、视觉重心和表达方式，再生成页面结构。理论上可以自由组合文本、形状、连接线、图标、SVG 和图表，而不必局限于预制模板。

这一路线的吸引力在于：**页面结构可以由内容决定，而不是由模板决定。**

但实际工程中发现，LLM 的自由编排能力与最终 PPTX 的可表达能力之间，存在明显差距。

本项目最终采用以低阶 PowerPoint 元素为主的 Scene Graph，使 LLM 尽量自主决定布局，同时由 PptxGenJS 将图层转换为可编辑对象。

这比固定模板更灵活，但没有彻底解决排版质量问题。

## 三、实践中最值得分享的几个问题

### 1. LLM 能设计页面，不代表能稳定输出高质量 PPTX

在交互式对话中，直接向 LLM 提供简单设计提示词和完整正文，往往可以得到不错的 HTML 页面。

但将同一任务放进程序，要求模型生成符合严格 Schema 的 Scene-Graph JSON，再映射为 PPTX，效果可能明显下降。

原因之一是模型不仅需要理解与设计内容，还需要同时考虑坐标、元素类型、字段规范、文字容纳空间和导出兼容性。

**经验：结构化输出有利于工程稳定，但复杂的输出协议也可能压缩模型的设计自由度。**

### 2. 代码纠偏不一定改善视觉质量

早期为了保证输出稳定，项目增加了自动布局、卡片合并、文本压缩、颜色修正、布局评分、导出一致性检查等机制。

这些机制能够解决部分异常，却也带来新的问题：

- 自动等分空间，导致卡片和模块机械化。
- 为避免文字溢出而缩小字体，破坏视觉层级。
- 为避免重叠而移动元素，造成新的留白和位置偏差。
- 过度使用保守颜色、浅色填充和边框，使页面缺少视觉重点。
- 不必要的质量拦截增加了生成失败和重试成本。

后续尝试减少自动布局和审美干预，只保留必要的结构合法性、安全检查与导出处理。

**经验：代码适合保证数据和文件正确性，不一定适合替代 LLM 做审美决策。**

### 3. PPTX 可编辑性与视觉表现存在工程取舍

HTML/CSS 的布局和视觉表达能力非常丰富，但 PowerPoint 的形状、文本框和图形系统并不等同于浏览器渲染系统。

例如：

- HTML 与 PowerPoint 的字体度量、换行和文本框内边距不同。
- 复杂布局在转换成独立形状后，可能失去原有的视觉关系。
- SVG 可以嵌入 PPTX，但不等于其中每个元素都能原生编辑。
- 一些高级图形效果在导出库中缺少直接支持。

我们还尝试过使用多个透明色块模拟渐变填充，最终效果却像一组拼接矩形，不仅影响美观，还增加了不必要的图层复杂度。

**经验：PPTX 文件能成功导出、元素能够编辑，与最终排版达到人工设计水平，是三个不同的问题。**

### 4. 高阶组件不一定比基础图层更灵活

项目早期支持了流程、矩阵、时间轴、对比、漏斗等多种高阶组件。

但当组件内部的空间分配、文本高度和元素位置由代码决定时，本质上仍然存在隐性的模板约束。

例如，流程组件可能自动等分所有节点，但不同节点的内容量并不相同。

后期转向由 LLM 直接输出文本框、形状、线条和连接线等基础图层，让模型自主组合复杂结构。

**经验：在追求非模板化设计时，组件抽象程度越高，不一定意味着视觉自由度越高。**

### 5. 简单 Prompt 有时比复杂规则更有效

在另一个 HTML 编排项目的实践中，我们发现一种相对简洁的输入结构效果较好：

```text
# 通用编排要求（固定）
# 色调风格（可选）
# 以下是本页内容
【完整分页正文】
```

通用部分只描述设计目标、画布规范、视觉层级、阅读路径与必要的技术边界。

具体采用流程、矩阵、对比还是图解，由 LLM 根据内容自主判断。

这也促使本项目后期减少复杂的 Page Plan、模板规则和多阶段生成逻辑，尝试让单次 LLM 调用直接完成单页设计。

不过，这种方法在 HTML 输出上观察到的优势，并不意味着它能够直接解决 PPTX 的转换问题。

## 四、关于模型能力的个人观察

开发过程中尝试过多种常见国产大模型的完整规格版本，希望依靠模型自身的理解、结构化输出和排版能力完成单页设计。

从个人测试体验来看，**DeepSeek 和 Qwen（通义千问）系列的表现相对更好**，但整体结果仍未达到预期的 PPTX 排版质量。

需要说明：

- 这只是特定项目、提示词和测试样本下的主观观察，并非标准化模型评测。
- 不同模型版本、参数、结构化输出方式和 Prompt 都可能显著影响结果。
- 最终视觉效果还受到 Scene Graph、导出组件和 PowerPoint 渲染机制的影响，不能简单归因于模型能力。
- 模型发展很快，未来更强的模型或更适合的生成架构，可能改变当前的结论。

**因此，这里的结果不代表某个模型无法完成 PPT 设计，只代表本项目采用的技术链路尚未实现理想效果。**

## 五、项目现状与后续方向

### 当前项目：停止继续开发

本项目已经完成基础端到端流程，并探索了多种 Scene-Graph、自动布局、低阶图层以及 PPTX 导出方案。

但从实际效果看，可编辑 PPTX 的排版质量仍未达到最初期望。

继续在当前架构上增加组件、修补布局规则，可能带来较高的工程复杂度，却不一定产生相应的视觉质量收益。

因此决定停止本项目的后续功能开发，将代码作为实验性实现公开，供感兴趣的开发者阅读、参考和自行探索。

### 后续探索：转向 HTML-first 可视化编排

接下来的探索将转向另一条路线：

```text
非结构化正文
    ↓
LLM 直接生成 HTML/CSS 幻灯片
    ↓
HTML 可视化预览与编辑
    ↓
结合 Lumenfold 进行页面编排调整
```

Lumenfold 是另一个围绕幻灯片 HTML 页面编排与可视化处理的项目。

选择这条路线，主要因为 HTML/CSS 提供了更自由的布局与视觉表达能力，也更容易直接观察、修改 LLM 生成的页面。

这意味着暂时将重点从“自动生成完全可编辑的 PPTX”转向“高质量的幻灯片视觉编排”。

HTML 到高保真、可编辑 PPTX 的转换问题仍然存在，并没有因为更换路线而自动解决。

## 六、最后的一些思考

通过这个项目，我最大的体会是：

**LLM 自动生成 PPT 的难点，不只是模型能否理解内容，而是如何让模型的设计意图不在工程转换过程中丢失。**

模板化方案容易实现稳定输出，但可能牺牲内容适配能力；自由生成方案具有更大的视觉表达空间，却对模型、结构化协议、渲染引擎和输出格式提出了更高要求。

在两者之间，应该根据最终交付目标选择技术路线，而不是一味增加规则或组件。

如果目标是标准化、批量化、可编辑的报告，模板驱动可能更务实。

如果目标是单页高质量、灵活、接近人工设计的视觉编排，直接生成 HTML 并进行可视化调整，也许更值得探索。

本项目并没有找到完美答案，但这些尝试至少帮助明确了问题所在。

希望这份代码和实践总结，能让后来者少做一些无效的重复尝试，也欢迎基于此开展不同方向的实验。
